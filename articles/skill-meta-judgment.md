# AIエージェントに必要なのは「良い Skill」だけなのだろうか ― Skill、Experience、そして「今の自分の判断を信じてよいのか」を判断する能力について ―

本稿では、AIエージェントの Skill の有用性をより推し進めるために、熟練者の実務判断と暗黙知の扱いに着目しつつ、Skill が LLM の思考を固定してしまう可能性と、それを回避するために必要と思われる追加の枠組みについて論じていきます。

---

最近、AI エージェントにおける **Skill** が注目されています。

ある種類の作業をするときに、

- 何を確認するのか
- どの順番で進めるのか
- どのツールを使うのか
- どんな条件を満たす必要があるのか
- どこで人間に確認するのか

といった実務知識を、自然言語を中心とした再利用可能な形で記述し、AIエージェントに直接実行させる仕組みです。

これは、 非常に大きな可能性を持っています。

従来は、人間が持つ実務知識の多くは、マニュアルや書籍、設計書、研修、OJTなどを通して伝えられてきました。そしてそれを実施するのは人間でした。

ところが Skill では、人間が文章として記述した作業知識を、AI エージェント自身が読み、そのまま実行へつなげることができます。

これは **実行可能な作業単位の外部化**（他者でも利用可能にすること）と考えることができます。

つまり、ある意味では、ソフトウェアが「計算手順を実行可能な知識にした」という「革新」の次のレベルとして、Skill は、自然言語での記述力を活用し、幅広い人々が関与できるかたちで、人間の判断や作業手順を含む、より広い実務知識を、人間以外の主体にも実行させられる形へ変え始めているのかもしれません。

より詳細には、現在の Agent Skills の仕様を参照すると、Skill はまず `name` と `description` によって発見・選択され、必要と判断された時点で `SKILL.md` 本文が読み込まれ、さらに必要に応じて `references` や `scripts` が参照される Progressive Disclosure の構造をとります。つまり Skill は、「何をするか」だけでなく、「いつ自分が relevant なのか」を自然言語で Agent に伝える仕組みでもあります（[Agent Skills Specification](https://agentskills.io/specification)）。

私はこの Skill の可能性に強く惹かれています。

しかし同時に、最近ひとつの違和感を持つようになりました。

**よく整理された Skill を作れば、本当に熟練者のような判断と業務遂行ができるようになるのだろうか？**

AI エージェントは、実世界における複雑な作業においては弱さを露呈していると言われていますが、その理由のひとつは、単に Skill の不足や推論能力の限界だけではなく、人間の経験を整理された Skill へ変換する過程で、何か重要なものが失われているからではないか。

むしろ、Skill を詳細に、明確に、キレイに書けば書くほど、失われてしまうものがあるのではないか？ そんな風に考え始めました。

# 熟練者は「正しい手順」をたくさん知っている人なのか？

ここで、熟練したソフトウェア設計者のことを思い出してみましょう。  
ソフトウェアを設計しているとき、次のような状況に遭遇することがあります。

- 仕様は非常にキレイ
- データ構造も整っている
- 責務の分離も明確
- 抽象化もよくできている

一見すると、かなり良い設計に見えます。

ところが、経験のあるエンジニアがそれを見て、

> 「うーん。なんだか、ちょっと嫌な感じがするな」

と言うことがあります。

何が悪いのか聞いても、最初から明確に説明できるとは限りません。

- 「仕様がキレイすぎる気がする」
- 「後で要求が変わったとき、逃げ道がなくなりそう」
- 「似たような設計で酷い目にあった気がする」
- 「うまく説明できないけど、ただこの構造は不快なんだ」

そんなちょっと曖昧な言葉が返ってくることがあります。

注目すべきは、**仕様が綺麗であること自体は、本来は悪いことではない** という点です。

にもかかわらず、過去に何度も設計し、運用し、失敗し、修正してきた人は、**ある特定のキレイさ** に、何らかの「異臭」を感じることがあります。

この感覚は、いったいどこから来るのでしょうか？

# 「失敗を Skill に書けばよい」では足りない？

この状況に対する解決策として思いつくのは、失敗事例を Skill に追加することです。

たとえば、

- 大規模テーブルではこの migration を避ける
- 要求変更の可能性が高い場合、この抽象化は使わない
- 過去にこの手順で障害が発生した

といった項目を増やしていく。

これは確かに有用です。

ソフトウェアも、バグが見つかるたびにテストを追加し、例外処理を追加し、再発を防ぎながら成熟してきました。

Skill でも同じことができるでしょう。

しかし、考えれば考えるほど、それだけでは熟練者の「嫌な匂い」の感知を再現できないように思えてきます。

なぜなら熟練者は、たとえば、

> 「これは過去の失敗事例 第42番 に一致するから、この設計は危険だ」

と判断しているわけではないからです。

- いくつもの成功
- いくつもの失敗
- 危うく失敗しそうになった経験
- 予想外だった出来事
- 最初はうまくいったのに、数か月後に問題になった設計
- 逆に、危険だと思ったのに意外とうまくいった経験

そうした大量の経験が積み重なった結果が、判断の際の違和感、

> 「これ、何か妙だな」

という形で表出しているように思えます。

つまり、失敗の経験がそのまま明示的なルールになっているとは限らない。

むしろ過去の多数の経験が混ざり合い、判断そのものの傾向を変えている。

これは明文化された if-then ルールというより、**多数の経験によって形成された分散的なパターン認識** に近いのかもしれません。

このような熟練者の判断は、認知科学でも長く研究されてきました。Gary Klein らが熟練した消防指揮官の意思決定を調べた研究では、複数の選択肢を並べて比較する場面は少なく、むしろ過去の経験から状況を「見覚えのあるパターン」として認識し、適切と思われる行動を直接想起する判断が多く観察されました。これは **Recognition-Primed Decision（RPD）** として整理されています（[Klein, Calderwood & Clinton-Cirocco, 1986](https://doi.org/10.1177/154193128603000616)）。

ただし、経験が多ければ直感が自動的に正しくなるわけではありません。Daniel Kahneman と Gary Klein は、熟練した直感が信頼に値するものとなるためには、環境に学習可能な規則性があり、その規則性について十分な経験とフィードバックを得られることが重要だと整理しています（[Kahneman & Klein, 2009](https://doi.org/10.1037/a0016755)）。つまり Experience を蓄積するだけでなく、**その経験と結果の対応を観測し、学べること** が必要になります。

# Procedural Knowledge と Episodic Knowledge

ここで、さらに議論を深めるために、今一度 Skill とは何なのかを整理してみます。

Skill が非常に得意なのは、

> **どうやるか**

を外部化することです。

つまり **Procedural Knowledge（手続き的知識）** です。

一方、熟練者は別の種類の知識も持っています。

> あのとき実際に何が起きたのか。

これは **Episodic Knowledge / Episodic Memory（エピソード的な知識・記憶）** と考えることができます。

なお、ここでは認知心理学における Episodic Memory と厳密に同一視するのではなく、文脈を伴った個別の経験を広く Episodic Experience と呼ぶことにします。

たとえば、

> 最初はうまく動いていた。  
> しかし顧客が 3社から 30社に増えたころ、例外処理が急増した。  
> 仕様変更のたびに抽象化の境界を破る必要が出てきた。  
> 最終的には、一見美しかった設計を大きく作り直した。

という経験です。

ここから、

> 「抽象化しすぎるな」

というルールを作ることはできます。

しかし、そのルールだけを抽出しても、経験そのものが持っていた情報の大部分は失われます。

- どのくらいキレイに見えていたのか
- どこまでは正常だったのか
- 最初の小さな兆候は何だったのか
- 当時なぜ問題ないと思ったのか
- 何が予想外だったのか
- どのタイミングならまだ簡単に戻れたのか
- 結果として何が一番高くついたのか

エピソードには、こうした文脈が残っています。

ルールは、これらの側面を削ぎ落として圧縮したものです。

こうした圧縮は、知識を再利用可能にするために必要です。

しかし、圧縮には情報損失があります。

もしかすると **熟練とは、ルールを大量に持っていることではなく、Procedural Knowledge と共に、複雑な体験に根ざした Episodic Experience の両方を使って判断することにより達成される** のではないでしょうか。

つまり私は、次のように考えるようになりました。

- **Skill の中心的な役割 = Procedural Knowledge の外部化**  
- **Experience = Episodic Knowledge**  
- **熟練した判断 = Semantic / Procedural Knowledge と Episodic Experience を背景に形成される Meta-Judgment**

ここで重要なのは、最後の **Meta-Judgment** です。

# 熟練者は答えより先に、判断の「確信度」を調整する

熟練者の特徴は、彼らが必ずしもすぐに正解を定めようとしている訳ではないということです。

場合によっては、むしろ、

> 「このまま進めるのはちょっと怖い」

と感じ、躊躇します。

これは「答え」ではありません。

しかし、そこに内在する不確定さを許容し、その低減を図るために、躊躇の後、行動を変えていきます。

- すぐ実装せず、もう少し調べる
- 要求の背景を聞き直す
- 小さく試す
- 可逆性の高い設計を選ぶ
- 決定を遅らせる
- あるいは、いったん Skill の適用そのものを止める

つまり Experience は、

`Experience ▶︎ Answer`

という形で働くとは限りません。

むしろ、

`Experience ▶︎ Meta-Judgment ▶︎ Action`

なのではないでしょうか。

熟練者は、過去の経験によって **現在の判断の確信度を調整し、ときには判断の前提や問題の捉え方そのものを疑う。**

「形式的にはこの Skill を適用できる。しかし、本当にそれで良いのだろうか？」

という問いを発生させる。

この違和感が、熟練者にとって非常に重要な安全装置になっているように思うのです。

# Skill は Agent の Attention を狭める装置にもなりうる

くわえて、Skill を増やしたり詳細化したりすることが、逆説的に問題になりうる、少し厄介な可能性を指摘しようと思います。

Skill は Agent に、

> この種類の問題では、こう考えなさい。

と教える仕組みです。

これは Skill の強みです。

しかし同じことを別の角度から見ると、

> この問題は、この枠組みで見なさい。

と Agent に Frame（思考の枠組み）を与える仕組みでもあります。

つまり Skill は、**問題を解決する知識であると同時に、Agent の Attention（着眼点）を狭める装置にもなりうる**。

これは人間にも見られる現象です。

認知心理学では、過去にうまくいった解法や馴染みのある問題表現が、新たに解こうとしている問題の見方を狭めてしまう **Einstellung Effect（構え効果）** が知られています。

心理学者のアブラハム・マズローが残した名言「ハンマーしか持っていなければ、すべてが釘に見える」を思い出す方もいるかもしれません。

熟練者でさえ、最初に「これはあのタイプの問題だ」と認識すると、その Frame に関連した特徴に注意が集中し、別の可能性を見落とすことがあります。

この点について、Merim Bilalić らがチェスの熟練者を対象に行った研究は示唆的です。馴染みのある解が最初に思い浮かぶと、より良い解が存在してもそれを発見しにくくなりました。さらに Eye Tracking を用いた実験では、参加者自身は「より良い別解を探している」と報告しているにもかかわらず、視線は最初に活性化された解に関係する盤面の特徴へ留まり続ける傾向が観測されました。つまり **既存の Frame は、答えだけでなく 「何を見るか」という Attention そのものに影響** していたことになります（[Bilalić, McLeod & Gobet, 2008](https://doi.org/10.1016/j.cognition.2008.05.005)）。

もちろん、これは人間についての研究であり、Skill を持つ LLM Agent で同じ現象が起きることを直接示したものではありません。しかし、「先に与えられた Frame が、その後に何を見るかを変える」という点は、本稿の問題意識とよく重なります。

Skill を扱う Agent でも、似たことが起きる可能性があります。

つまり、

```text
曖昧な現実
    ▼
Skill A が関連があるように見える
    ▼
Skill A を読み込む
    ▼
Skill A が分類軸・注意点・判断基準を与える
    ▼
その Frame で状況を整理する
    ▼
Skill A と整合する証拠がさらに目につく
    ▼
「やはりSkill Aで正しい」
```

という自己強化ループです。

**特に LLM は、与えられた Instruction や Context を、できるだけ整合的な解釈にまとめようとする傾向があるように見える。**

ここでは便宜的に、

- 構造化された説明へ寄せようとする傾向
- 与えられた前提との認知的整合性を維持しようとする傾向
- 複数の曖昧な可能性をひとつの説明へ収束させようとする傾向

と整理してみましょう。

これらを LLM の認知バイアスとしてそのまま結論づけることには慎重であるべきですが、少なくとも実務上、

> **強い Skill を与えることで、Agent がその Skill に合うように世界を見始める**

可能性は考えておく必要があります。

Skill が詳細に厳密によくできているほど、より危険になる場合すらあるかもしれません。

この可能性を Agent Skills 側から考えるうえで興味深い研究も現れています。2026年の *Under the Hood of SKILL.md* では、`SKILL.md` の自然言語的な Metadata や Description の Framing によって、機能的には同等な Skill のどちらを Agent が選ぶかが偏りうることが報告されました（[Saha, Faghih & Feizi, 2026](https://arxiv.org/abs/2605.11418)）。この研究が、本稿でいう「Skill を読み込んだ後の Frame Fixation」まで実証したわけではありません。しかし少なくとも、**SKILL.md は受動的な説明文ではなく、Agent が何を見つけ、選び、使うかに影響する Operational Text である** ことを示す結果だと言えます。

# 現在の状況を Skill の Frame に押し込めていないか？

現在の Skill 設計では、

> いつこの Skill を使うか

を書くことはできます。

さらに、

> この条件では使ってはいけない

という条件を書くこともできます。

これは重要です。

しかし、熟練者の判断にはもう一つ別のレベルがあります。

> **自分が、この状況を既知のカテゴリーへ無理に押し込めようとしていないか？**

という疑いです。

これは単なる例外ルールではありません。

「A なら Skill を使う」「B なら使わない」という一段上に、

> **そもそも A や B という現在の分類を信頼してよいのか？**

という問いがあります。

言い換えれば、

> 「ルールをどう適用するか」

ではなく、

> **「このルール体系をいま適用すること自体が妥当なのか」**

を判断する能力です。

これは単なる Skill Selection とは少し違います。

Skill Selection が、

> A、B、C のどの Skill が最も適切か

を問うのに対して、

Meta-Judgment は、

> **A、B、C のいずれかで処理できると思っていること自体が間違っていないか？**

を問います。

# Execution-Oriented から Risk-Sensitive へ

現在の AI エージェントの評価では、

> タスクを最後まで遂行できたか

が大きく注目されます。

当然重要です。

しかし実世界の作業では、最後まで遂行すること自体が目的ではありません。

- 時には、途中で止まる方が正しい
- そして追加情報を集めた方がよい
- 判断を保留した方がよい
- 可逆的な一歩だけ進めた方がよい

熟練者はこのようにして、実世界の不確定性と Risk を考慮しつつ、遂行を調整します。

つまり Agent に必要なのは、

**Execution-Oriented**

な姿勢だけではなく、

**Risk-Sensitive**

な姿勢です。

「できるか」だけではなく、

- 今やるべきなのか
- どこまでやるべきなのか
- 間違っていた場合に戻れるのか
- 何がまだ分かっていないのか
- 今の確信は何に依存しているのか

を考慮する必要があります。

実務における成功は、常にその場の最適解を選ぶことではありません。

- 多少遠回りに見えても、将来的な選択肢を残す
- 手戻り可能な状態を保つ
- 不確実性が高いときには、大きな不可逆な決断を避ける

こうした判断を積み重ねることで、

**将来の不確実性の中で、成功可能性を維持する**

ことができます。

**プロジェクトの成功は、成功か失敗かという一度きりの２値判定ではなく、成功確率を少しずつ上げ続ける判断の連続** として捉えた方が、実態に近いと思われます。

実際、私が知っている経験豊富なプロジェクトマネージャー達は、判断する事項と保留する事項の仕分けを的確に行いつつ、最終的なプロジェクト成功確率を着実に上げていきます。

# 「成功」と「失敗」だけを記録しても足りない

近年、LLM Agent がより長期的で複雑な作業を担うようになるにつれ、Agent Memory の研究も盛んになっています。

しかしながら、ここまでの議論から考えると、Agent の経験を記録するときにも、

- SUCCESS
- FAILURE

という二値だけでは不十分です。

実務の経験には、もっと微妙なものがあります。

- 成功したが、危なかった
- 想定とは違ったが、結果的には問題にならなかった
- その場では成功したが、数か月後に副作用が出た
- 失敗したが、その判断自体は当時の情報では妥当だった

特に重要なのは、**Near Miss（失敗には至らなかった危険な経験）** と **Surprise（想定外の状況）** だと思います。

重大事故だけが経験を作るわけではありません。

「今回は大丈夫だったけれど、あれはちょっと危なかった」

「あれ？ 思っていたのと違う」

という小さな経験の積み重ねが、熟練者の感覚を形成します。

つまり Agent の経験を蓄積するなら、

> 成功したか失敗したか

だけでなく、

> **予想通りだったか、予想外だったか**

という軸が重要になる可能性があります。

こうした考え方には、人間の組織側にも長い蓄積があります。High Reliability Organization（HRO）の研究では、重大事故だけでなく Incident や Near Miss をシステムの状態を示す Signal として扱い、**Preoccupation with Failure（失敗への継続的な警戒）** や **Reluctance to Simplify（安易に単純化しない姿勢）** が重視されてきました。英国の石油精製施設を対象とした事例研究でも、Incident や Near Miss の収集・分析が Reliability を高める実践の一部として報告されています（[Lekka & Sugden, 2011](https://doi.org/10.1016/j.psep.2011.07.003)）。

「成功したから問題なし」で終わらせるのではなく、**成功したにもかかわらず、なぜ危なかったのか** を学習材料にする。この発想は、熟練した Agent の Experience を考えるうえでも重要なのではないでしょうか。

# 失敗をルール化すれば安全になる、とは限らない

ここでもう一つ注意したいことがあります。

失敗を経験するたびに、

> この場合は禁止  
> この場合は確認  
> この場合は別手順

というルールを増やしていけば、Skill は確かに詳細になります。

しかし、

```text
Failure
   ▼
New Rule
   ▼
More Rules
   ▼
Safer Agent
```

と単純に進むとは限りません。

ルールが増えるほど Agent が既存の分類体系へ依存し、

> 「このケースはルール42番だ」

と処理するようになれば、未知のケースへの柔軟性が落ちる可能性があります。

過去の失敗から学んだはずなのに、その学び方が Procedural になりすぎることで、かえって未知の状況へ弱くなる。

実際、448組織を対象に Near Miss からの学習を調べた研究では、Near Miss の経験は組織の **Procedural Response を強める一方で、Flexible Response への重点を弱める** 傾向と関連していました（[Azadegan et al., 2019](https://doi.org/10.1016/j.ijpe.2019.04.021)）。もちろん、組織と LLM Agent をそのまま同一視することはできません。しかし「失敗から学ぶこと」と「ルールを増やすこと」は同義ではなく、学び方によっては柔軟性を失う可能性がある、という点は示唆的です。

これはまた、人間の組織でも良く経験される問題にも似ています。

- 事故が起きる
- チェックリストが増える
- 承認フローが増える
- 禁止事項が増える

しかし本当に必要だったのは、

> 「なぜ我々は、そもそもこの状況を安全だと判断したのか」

を疑うことだった、ということがあります。

組織学習の研究でいう **Single-loop Learning** と **Double-loop Learning** の違いにも近いでしょう。Chris Argyris は、与えられた目的や前提の中で誤りを修正するだけでなく、その判断を生み出した Policy や Objective 自体を問い直す学習を Double-loop Learning として区別しました（[Argyris, 1977](https://hbr.org/1977/09/double-loop-learning-in-organizations)）。

失敗した行動を修正するのが Single-loop。  
判断を生み出した前提や Frame そのものを疑うのが Double-loop です。

Skill の改善も、間違った直接の原因である特定の Step を書き換えるだけでは Single-loop に留まる可能性があります。

本当に問うべきなのは、

> **なぜ Agent は、この状況でこの Skill を使うことが妥当だと思ったのか**

ではないでしょうか？

# Experience を、すぐルールに変換しない

ここで重要になるのが、Experience の扱いです。

AI に経験を学ばせようとすると、私たちはすぐに、

> そこから一般化可能なルールを抽出しよう

と考えます。

もちろん、それは非常に有用です。

大量の Episode（個別経験）を毎回そのまま LLM の Context へ入れることは不可能か、可能であっても効率的ではありません。

何らかの圧縮や検索による選択的適用は必要になります。

一方で、Memory を構造化・圧縮する過程そのものが文脈を壊す可能性を問題にする研究も現れています。

2026年に発表された E-mem という Memory システムでは、複雑な Episode を Embedding や Graph などの事前定義構造へ圧縮すると、長い時間軸にまたがる Contextual Dependency が損なわれうることを **Destructive De-contextualization** として問題化し、Episodic Context を再構成する方向を提案しています（[Wang et al., 2026](https://arxiv.org/abs/2601.21714)）。

つまり、あらゆる Experience をすぐルールへ変換してしまうと、今まさに守ろうとしているものを失う可能性があるということです。

たとえば、

> 「この抽象化は複雑化するので避ける」

というルールだけを残すと、

- 「なぜ最初は魅力的に見えたのか」
- 「どの程度までなら問題なかったのか」
- 「何が最初の異変だったのか」
- 「どの時点で判断を変えることができたのか」

といった Episode 特有の情報は消えます。

もしかすると Agent には、

**Generalized Knowledge**

だけでなく、

**Unresolved Experience**

も必要なのではないでしょうか。

ここで、Unresolved Experience とは、**まだ安定した一般則へ還元できないが、将来の Meta-Judgment で価値を持つ Episode** のことです。

- まだ綺麗な教訓にできない経験
- 説明し切れない違和感
- 結果だけを見ると成功だが、何かがおかしかった Skill の実行

そうしたものを、無理に整理・分類せずに残す。

これもまた、Skill の世界に必要な知識形式だと思います。

なお、本稿でいう Unresolved Experience は 上述の E-mem のアプローチとは異なります。しかし、「Memory を整理すればするほど良い」とは限らず、**Episode が持つ文脈をどこまで残すべきか** が独立した設計問題になる、という点では強く関連しています。

# Skill / Experience / Meta-Judgment

ここまでの議論を、暫定的に三つの層として整理してみます。

![Skill Meta-Judgment](/images/skill-meta-judgment/skill-meta-judgment-diagram.png =350x)

Skill は **What to do / How to do** を与える。

Experience は **what actually happened** を保持する。

Meta-Judgment は、

> **いま自分が「やるべきだ」と思っていることを、どこまで信頼してよいのか**

を判断する。

つまり、Meta-Judgment は Knowledge（知識表現）というより、二種類の知識 + それらを状況に応じて制御する一段上の判断層、つまり、Knowledge の利用に際する Control / Judgment Mechanism と言えます。

現在の Agent Skills は、１つ目の Skill Layer を急速に発展させています。

Agent Memory の研究は、２つ目の Experience Layer へ取り組み始めています。

そして、**まだ十分に整理されていないのが、３つ目の Meta-Judgment Layer なのではないか** と考えています。

# In-context experience は「直感」として機能しうるのか？

ここで LLM には、従来のソフトウェアにはなかった興味深い特性があることについて言及してみましょう。

それは、**In-context learning（文脈内学習）** ができることです。

これは、追加学習でモデルのパラメーターを更新しなくても、例、過去の経験、追加情報などを Context として与えることで、その Context に応じて振る舞いを変化させることができるという LLM の特徴のことです。

すでに LLM Agent 研究では、過去の Trial、Reflection、Trajectory、成功・失敗事例などを Context として与えることで、次の実行へ利用し、性能を改善するアプローチが多数行われています。

代表例のひとつである **Reflexion** は、モデルの Weight を更新する代わりに、Task の Feedback を自然言語で Reflection し、そのテキストを Episodic Memory Buffer に保存して次の Trial に利用します（[Shinn et al., 2023](https://papers.neurips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html)）。また **ExpeL** は、Agent が複数の Task から Experience を蓄積し、そこから抽出した Insight と過去の Experience 自体を、推論時に想起して判断へ利用する枠組みを提案しています（[Zhao et al., 2023](https://arxiv.org/abs/2308.10144)）。

これらの研究は、「Weight を再学習しなくても、過去の Experience を利用して Agent の性能を改善できる」ことを示しています。しかし本稿で特に関心があるのは、そこからさらに踏み込んだ、少々違う問いです。**Experience によって正答率を上げるだけでなく、Agent の「疑い方」そのものを変えられるのか、というポイントです。**

つまり、この能力を、

> **Agent の判断姿勢そのものを変えるため**

に使うことはできないでしょうか？

たとえば同じ Skill と同じ未知タスクを与えます。

Experience を与えていない Agent は、

> 「条件を満たしているので、この Skill を実行します」

と判断する。

一方、過去の多様な episode を読んだ Agent は、

> 「形式上はこの Skill を適用できます。しかし、過去のいくつかのケースでは、同様に前提が綺麗に揃って見えたときほど、後から未確認の制約が発見されています。実行前に X を確認します」

と判断する。

もしこのような変化が起きるなら、それは非常に興味深い。
これは単に、

**正答率が上がった**

のではありません。  
Agent の推論姿勢が、

**Execution-Oriented**

から、

**Risk-Sensitive**

へ変化したことになります。

言い換えれば、

> **In-context experience が、熟練者の Intuition（直感）の初歩的な代替になった**

と考えられる可能性があります。

もちろん、本当にそうなるかどうかは、実際に実験してみなければ分かりません。

# 何を評価すべきなのか

注意が必要なのは、この仮説を検証する場合、従来的な判断基準だけでは足りないということです。  
「タスクを成功させたか」だけを測ると、重要な変化を見落とします。

むしろ、

- 疑うべきところで疑ったか
- 不足情報に気づいたか
- Skillが想定していない兆候を拾ったか
- 追加観測を選んだか
- より可逆的な行動を選んだか
- Skillの適用そのものを中止できたか

といったものを測る必要があります。

この問題に近い研究は、すでに始まりつつあります。2026年の **Agentic Abstention** は、Agent が単発で「答える／拒否する」を選ぶ問題ではなく、環境との相互作用の途中で **Answer / Act / Abstain** を逐次判断し、「いつ行動を止めるべきか」を扱っています。13種類の LLM-as-Agent システムを 28,000 件以上の Task で評価した結果、止まるべきなのに止まれないケースだけでなく、止まる判断が遅すぎるケースも観測されています（[Luo, Wen & Wang, 2026](https://arxiv.org/abs/2606.28733)）。

これは本稿の問題意識と非常に近い一方で、Meta-Judgment は単なる停止判断より少し広いものとして考えています。つまり、「行動を続けるべきか」だけでなく、**そもそも現在の Problem Frame や Skill の適用そのものを信頼してよいか** を問う層です。

つまり、

> **Can the agent execute the skill?**

だけではなく、

> **Does the agent know when not to trust the skill?**

を測る。

これは Skill の評価そのものを変える可能性があります。

# Skill をさらに有用にするための新たな視点

Agent Skills は、とても魅力的な枠組みです。

人間が長年かけて身につけてきた業務手順や判断基準を自然言語で記述し、AI エージェントにそのまま実行させられる。

これは人類の実務知を、実行可能な形へ外部化する大きな一歩になるかもしれません。

しかし、その可能性が大きいからこそ、

> **Skill に熟練そのものを期待しすぎない**

ことに留意が必要だと思います。

Skill は Procedural knowledge を外部化できます。

しかし熟練者は Procedural Knowledge だけで動いているわけではありません。

世界についての一般知識がある。

大量の Episode（個別経験）がある。

失敗だけでなく、near miss や surprise がある。

そして、それらを背景に、

> 「今回は少し違うかもしれない」

と自分自身の判断を疑います。

もしそうなら、

```text
良い Skill ─▶ 良い Agent
```

という単純な構図ではなく、

```text
Semantic Knowledge   ─┐
Procedural Knowledge ─┼─▶ Meta-Judgment ─▶ Situated Action
Episodic Experience  ─┘
```

という多層的なモデルで Agent を考えた方がよいのかもしれません。

# 判断の枠組みすら疑える AI Agent に向けて

考えてみると、人類は知識を共有するとき、長いあいだ経験を圧縮してきました。

- 経験から言葉を作る
- 言葉から概念を作る
- 概念から原則を作る
- 原則からルールを作る
- ルールからマニュアルを作る

Skill は、その延長線上にあります。

そして今までのマニュアルと大きく違うのは、Skill として記述されたルールを、AI エージェントが直接遂行できることです。

これは大きな変化です。

しかし、もし経験をルールへ変換すると、その圧縮過程で、私たちは何かを捨てています。

- 曖昧さ
- 例外
- 迷い
- 偶然
- 時間的な文脈
- まだ説明できない違和感
- 「なぜか分からないけれど、これはちょっと怖い」という感覚

これまで、そうしたものの多くは、人間の身体や記憶、職場の文化、師弟関係、レビュー、雑談、失敗談の中に残されてきました。

AIエージェントへ Procedural Knowledge を渡す技術は、急速に整いつつあります。

では、

> **Experience をどう渡すのでしょうか。**

そしてさらに、

> **Experience を使って、「いま自分が信じている Skill や Frame を疑う能力」をどう作るのでしょうか。**

これは、Agent Skills が成熟していく過程で、かなり重要な問いになるように思います。

Skill を書くことだけが、Agent に知識を与える方法ではないのかもしれません。

もしかするとこれから必要になるのは、

**Skill を教えること**

と同じくらい、

**経験させること**

なのではないでしょうか。

そして熟練した Agent とは、

たくさんの Skill を持つ Agent ではなく、

> **Skill を知り、Experience を持ち、それでもなお「今回は違うかもしれない」と疑える Agent**

なのかもしれません。

まだこれは仮説です。
しかし、十分に実験する価値のある仮説ではないかと思います。
あなたはどう思いますか？
