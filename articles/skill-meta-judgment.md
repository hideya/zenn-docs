# AIエージェントに必要なのは「良い Skill」だけなのだろうか ― Skill、Experience、そして「いま自分の判断を信じてよいのか」を判断する能力について

本稿では、AIエージェントの Skill の有用性をより推し進めるために、熟練者のプロジェクト管理の特徴と暗黙知の扱いに着目しつつ、Skill が LLLM の思考を固定してしまう可能性と、それを回避するために必要と思われる追加の枠組みについて論じていきます。

---

AIエージェントにおける **Skill** が注目されています。

ある種類の作業をするときに、

- 何を確認するのか
- どの順番で進めるのか
- どのツールを使うのか
- どんな条件を満たす必要があるのか
- どこで人間に確認するのか

といった実務知識を、自然言語を中心とした再利用可能な形で記述し、AIエージェントに直接実行させる仕組みです。

これは、 非常に大きな可能性を持っています。

従来は、人間が持つ実務知識の多くは、マニュアルや書籍、設計書、研修、OJTなどを通して伝えられてきました。そしてそれを実施するのは人間でした。

ところが Skill では、人間が文章として記述した作業知識を、AI エージェント自身が読み、そのまま行動へつなげることができます。

これは **実行可能な作業単位** の外部化と考えることができます。
つまり、ある意味では、ソフトウェアが「計算手順を実行可能な知識にした」という「革新」の次のレベルとして、Skill は、自然言語での記述力を活用し、幅広い人々が関与できるかたちで、人間の判断や作業手順を含む、より広い実務知識を、人以外でも実行可能な形へ変え始めているのかもしれません。

私はこの可能性に強く惹かれています。

しかし同時に、最近ひとつの違和感を持つようになりました。

**よく整理された Skill を作れば、本当に熟練者のような判断と業務遂行ができるようになるのだろうか？**

AI エージェントが実世界の複雑な作業で弱さを見せる理由のひとつは、単に Skill の不足や推論能力が足りないからではなく、

むしろ、Skill を詳細に、明確に、綺麗に書けば書くほど、失われてしまうものがあるのではないか？ そんな風に考え始めました。

# 熟練者は「正しい手順」をたくさん知っている人なのか？

ここで、熟練したソフトウェア設計者のことを思い出してみましょう。  
ソフトウェアを設計しているとき、次のような状況に遭遇することがあります。

- 仕様は非常にキレイ
- データ構造も整っている
- 責務の分離も明確
- 抽象化もよくできている

一見すると、かなり良い設計に見えます。

ところが、経験のあるエンジニアがそれを見て、

> 「うーん。なんだか、ちょっと嫌な感じがするな」

と言うことがあります。

何が悪いのか聞いても、最初から明確に説明できるとは限りません。

- 「仕様が綺麗すぎる気がする」
- 「後で要求が変わったとき、逃げ道がなくなりそう」
- 「似たような設計で酷い目にあった気がする」

そんなちょっと曖昧な言葉が返ってくることがあります。

注目すべきは、**仕様がキレイであること自体は、本来は悪いことではない** という点です。

にもかかわらず、過去に何度も設計し、運用し、失敗し、修正してきた人は、**ある特定のキレイさ** に、何かの「異臭」を感じることがあります。

では、この感覚はどこから来るのでしょうか？

# 「失敗を Skill に書けばよい」では足りない？

この状況に対する解決策として思いつくのは、失敗事例を Skill に追加することです。

たとえば、

- 大規模テーブルではこの migration を避ける
- 要求変更の可能性が高い場合、この抽象化は使わない
- 過去にこの手順で障害が発生した

といった項目を増やしていく。

これは確かに有用です。

ソフトウェアも、バグが見つかるたびにテストを追加し、例外処理を追加し、再発を防ぎながら成熟してきました。

Skill でも同じことができるでしょう。

しかし、考えれば考えるほど、それだけでは熟練者の「嫌な匂い」の感知を再現できないように思えてきます。

なぜなら熟練者は、

> 「過去の失敗事例 #42 に一致するから、この設計は危険だ」

と判断しているわけではないからです。

- いくつもの成功
- いくつもの失敗
- 危うく失敗しそうになった経験
- 予想外だった出来事
- 最初はうまくいったのに、数か月後に問題になった設計
- 逆に、危険だと思ったのに意外とうまくいった経験

そうした大量の経験が積み重なった結果が、判断の際の違和感、

> 「これ、何か妙だな」

という形で表出しているように見えます。

つまり、失敗の経験がそのまま明示的なルールになっているとは限らない。

むしろ過去の多数の経験が混ざり合い、判断そのものの傾向を変えている。

これは明文化された if-then ルールというより、**多数の経験によって形成された分散的なパターン認識** に近いのかもしれません。

# Procedural Knowledge と Episodic Knowledge

ここで、さらに議論を深めるために、今一度 Skill とは何なのかを整理してみます。

Skill が非常に得意なのは、

> **どうやるか**

を外部化することです。

つまり **Procedural Knowledge（手続き的知識）** です。

一方、熟練者はもう一つの種類の知識を持っています。

> あのとき実際に何が起きたのか。

これは **Episodic Knowledge / Wpisodic Memory（エピソード的な知識・記憶）** と考えることができます。

たとえば、

> 最初はうまく動いていた。  
> しかし顧客が 3社から 30社に増えたころ、例外処理が急増した。  
> 仕様変更のたびに抽象化の境界を破る必要が出てきた。  
> 最終的には、一見美しかった設計を大きく作り直した。

という経験です。

ここから、

> 「抽象化しすぎるな」

というルールを作ることはできます。

しかし、そのルールだけを渡しても、経験そのものが持っていた情報の大部分は失われます。

- どのくらいキレイに見えていたのか
- どこまでは正常だったのか
- 最初の小さな兆候は何だったのか
- 当時なぜ問題ないと思ったのか
- 何が予想外だったのか
- どのタイミングならまだ簡単に戻れたのか
- 結果として何が一番高くついたのか

エピソードには、こうした文脈が残っています。

ルールは、これらの側面を削ぎ落として圧縮したものです。

こうした圧縮は、知識を再利用可能にするために必要です。

しかし、圧縮には情報損失があります。

もしかすると **熟練とは、ルールを大量に持っていることではなく、Procedural Knowledge と共に、複雑な体験に根ざした Episodic Experience の両方を使って判断すること** なのではないでしょうか。

つまり私は最近、次のように考えるようになりました。

- **Skill = Procedural Knowledge**  
- **Experience = Episodic Knowledge**  
- **熟練 = Procedural Knowledge × Episodic Memory から形成される Meta-Judgment**

ここで重要なのは、最後の **Meta-Judgment** です。

# 熟練者は答えより先に、判断の「確信度」を調整する

熟練者の特徴は、彼らが必ずしもすぐに正解を定めようとする訳ではないということです。

むしろ、場合によっては、

> 「このまま進めるのはちょっと怖い」

と感じます。

これは答えではありません。

しかしそこに内在する不確定さを許容し、その低減を図るために、行動を変えます。

- すぐ実装せず、もう少し調べる
- 要求の背景を聞き直す
- 小さく試す
- 可逆性の高い設計を選ぶ
- 決定を遅らせる
- あるいは、いったん Skill の適用そのものを止める

つまり Experience（体験）は、

`Experience → Answer`

という形で働くとは限りません。

むしろ、

`Experience → Meta-Judgment → Action`

なのではないでしょうか。

熟練者は、過去の経験によって、現在の判断の **確信度** を調整する。

「形式的にはこの Skill を適用できる。しかし、本当にそうだろうか」

という問いを発生させる。

この違和感が、熟練者にとって非常に重要な安全装置になっているように思います。

# Skill は Agent の Attention を狭める装置にもなりうる

加えて、Skill を増やしたり詳細化したりすることが、逆説的に問題になりうる、少し厄介な可能性を指摘しようと思います。

Skill は Agent に、

> この種類の問題では、こう考えなさい。

と教える仕組みです。

これは Skill の強みです。

しかし同じことを別の角度から見ると、

> この問題は、この枠組みで見なさい。

と Agent に Frame（思考の枠組み）を与える仕組みでもあります。

つまり Skill は、**問題を解決する知識であると同時に、Agent の Attention（着眼点）を狭める装置にもなりうる**。

これは人間にも見られる現象です。

認知心理学では、過去にうまくいった解法や馴染みのある問題表現が、新たに解こうとしている問題の見方を狭めてしまう **Einstellung Effect（構え効果）** が知られています。

心理学者のアブラハム・マズローが残した名言「金槌しか持っていなければ、すべてが釘のように見える」を思い出す方もいるかもしれません。

熟練者でさえ、最初に「これはあのタイプの問題だ」と認識すると、その Frame に関連した特徴に注意が集中し、別の可能性を見落とすことがあります。

Skill を持った Agent でも、似たことが起きる可能性があります。

たとえば、

```text
曖昧な現実
    ↓
Skill A が関連があるように見える
    ↓
Skill A を読み込む
    ↓
Skill A が分類軸・注意点・判断基準を与える
    ↓
その Frame で状況を整理する
    ↓
Skill A と整合する証拠がさらに目につく
    ↓
「やはりSkill Aで正しい」
```

という自己強化ループです。

**特に LLM は、与えられた Instruction や Context のすべてを、何らかの整合的な解釈へまとめようとする傾向があります。**

ここでは便宜的に、

- 構造化された説明へ寄せようとする傾向
- 与えられた前提との認知的整合性を維持しようとする傾向
- 複数の曖昧な可能性をひとつの説明へ収束させようとする傾向

と整理してみましょう。

これらを LLM の心理学的バイアスとしてそのまま結論づけることには慎重であるべきですが、少なくとも実務上、

> **強い Skill を与えることで、Agent がその Skill に合うように世界を見始める**

可能性は考えておく必要があります。

Skill が詳細に厳密によくできているほど、より危険になる場合すらあるかもしれません。

# 現在の状況を Skill の Frame に押し込めていないか？

現在の Skill 設計では、

> いつこの Skill を使うか

を書くことはできます。

さらに、

> この条件では使ってはいけない

という条件を書くこともできます。

これは重要です。

しかし、熟練者の判断にはもう一つ別のレベルがあります。

> **自分が、この状況を既知のカテゴリーへ無理に押し込めようとしていないか？**

という疑いです。

これは単なる例外ルールではありません。

「A なら Skill を使う」「B なら使わない」という一段上に、

> **そもそも A や B という現在の分類を信頼してよいのか？**

という問いがあります。

言い換えれば、

> 「ルールをどう適用するか」

ではなく、

> **「このルール体系をいま適用すること自体が妥当なのか」**

を判断する能力です。

これは単なる Skill Selection とは少し違います。

Skill Selection が、

> A、B、Cのどの Skill が最も適切か

を問うのに対して、

Meta-Judgment は、

> **A、B、C のいずれかで処理できると思っていること自体が間違っていないか**

を問います。

# Execution-Oriented から Risk-Sensitive へ

現在の AI エージェントの評価では、

> タスクを最後まで遂行できたか

が大きく注目されます。

当然重要です。

しかし実世界の作業では、最後まで遂行すること自体が目的ではありません。

- 時には、途中で止まる方が正しい
- そして追加情報を集めた方がよい
- 判断を保留した方がよい
- 可逆的な一歩だけ進めた方がよい

そのようにして、実世界の不確定性と Risk を考慮しつつ、遂行を調整します。

つまり Agent に必要なのは、

**Execution-Oriented**

な姿勢だけではなく、

**Risk-Sensitive**

な姿勢です。

「できるか」だけではなく、

- 今やるべきなのか
- どこまでやるべきなのか
- 間違っていた場合に戻れるのか
- 何がまだ分かっていないのか
- 今の確信は何に依存しているのか

を見る必要があります。

実務における成功は、常にその場の最適解を選ぶことではありません。

- 多少遠回りに見えても、将来的な選択肢を残す
- 手戻り可能な状態を保つ
- 不確実性が高いときには、大きな不可逆な決断を避ける

こうした判断を積み重ねることで、

**将来の不確実性の中で、成功可能性を維持する**

ことができます。

**プロジェクトの成功は、成功か失敗かという一回の二値判定ではなく、成功確率を少しずつ上げ続ける判断の連続** として捉えた方が、実態に近いのかもしれません。

実際、私が知っている経験豊富なプロジェクトマネージャー達は、判断する事項と保留する事項の仕分けを的確に行いつつ、最終的なプロジェクト成功確率を上げていきます。

# 「成功」と「失敗」だけを記録しても足りない

最近、Skill 適用の広がりと、その運用上の要求から、Agent Memory の研究が進んでいます。

しかしながらあ、ここまでの議論から考えると、Agent の経験を記録するときにも、

- SUCCESS
- FAILURE

という二値だけでは不十分です。

実務の経験には、もっと微妙なものがあります。

- 成功したが、危なかった
- 想定とは違ったが、結果的には問題にならなかった
- その場では成功したが、数か月後に副作用が出た
- 失敗したが、その判断自体は当時の情報では妥当だった

特に重要なのは、**Near Miss（辛うじての成功）** と **Surprise（想定外の状況）** だと思います。

重大事故だけが経験を作るわけではありません。

「今回は大丈夫だったけれど、あれはちょっと危なかった」

「あれ？ 思っていたのと違う」

という小さな経験の積み重ねが、熟練者の感覚を形成します。

つまり Agent の経験を蓄積するなら、

> 成功したか失敗したか

だけでなく、

> **予想通りだったか、予想外だったか**

という軸が重要になる可能性があります。

# 失敗をルール化すれば安全になる、とは限らない

ここでもう一つ注意したいことがあります。

失敗を経験するたびに、

> この場合は禁止  
> この場合は確認  
> この場合は別手順

というルールを増やしていけば、Skill は確かに詳細になります。

しかし、

```text
Failure
   ↓
New Rule
   ↓
More Rules
   ↓
Safer Agent
```

と単純に進むとは限りません。

ルールが増えるほど Agent が既存の分類体系へ依存し、

> 「このケースはルール42番だ」

と処理するようになれば、未知のケースへの柔軟性が落ちる可能性があります。

過去の失敗から学んだはずなのに、その学び方が Procedural になりすぎることで、かえって未知の状況へ弱くなる。

これは、人間の組織でも知られている問題に似ています。

- 事故が起きる
- チェックリストが増える
- 承認フローが増える
- 禁止事項が増える

しかし本当に必要だったのは、

> 「なぜ我々は、そもそもこの状況を安全だと判断したのか」

を疑うことだった、ということがあります。

組織学習の研究でいう **Single-loop Learning** と **Double-loop Learning** の違いにも近いでしょう。

失敗した行動を修正するのが Single-loop。

判断を生み出した前提や Frame そのものを疑うのが Double-loop です。

Skill の改善も、間違った直接の原因である特定の Step を書き換えるだけでは Single-loop に留まる可能性があります。

本当に問うべきなのは、

> **なぜ Agent は、この状況でこの Skill を使うことが妥当だと思ったのか**

ではないでしょうか？

# Experience を、すぐルールに変換しない

ここで重要になるのが、Experience（体験）の扱いです。

AI に経験を学ばせようとすると、私たちはすぐに、

> そこから一般化可能なルールを抽出しよう

と考えます。

もちろん、それは非常に有用です。

大量の Episode（体験談）を毎回そのまま LLM の Context へ入れることは不可能か、可能であっても効率的ではありません。

何らかの圧縮や検索は必要になります。

しかし、あらゆる Experience をすぐルールへ変換してしまうと、まさに今守りたいものを失う可能性があります。

たとえば、

> 「この抽象化は複雑化するので避ける」

というルールだけを残すと、

- 「なぜ最初は魅力的に見えたのか」
- 「どの程度までなら問題なかったのか」
- 「何が最初の異変だったのか」
- 「どの時点で判断を変えることができたのか」

といった Episode 特有の情報は消えます。

もしかすると Agent には、

**Generalized Knowledge**

だけでなく、

**Unresolved Experience**

も必要なのではないでしょうか。

- まだ綺麗な教訓にできない経験
- 説明し切れない違和感
- 結果だけを見ると成功だが、何かがおかしかった Skill の実行

そうしたものを、無理に整理・分類せずに残す。

これもまた、Skill の世界に必要な知識形式だと思います。

# Skill / Experience / Meta-Judgment

ここまでの議論を、暫定的に三つの層として整理してみます。

```text
┌───────────────────────────┐
│        Meta-Judgment      │
│                           │
│  ・今の理解を信じてよいか     │
│  ・このSkillを使うべきか     │
│  ・さらに観察すべきか　　     │
│  ・止まるべきか　　　　　     │
│  ・人間へ戻すべきか　　　     │
└─────────────┬─────────────┘
              │
      ┌───────┴───────┐
      │               │
      ▼               ▼
┌───────────┐   ┌───────────┐
│   Skill   │   │ Experience│
│           │   │           │
│ how to do │   │ what      │
│           │   │ happened  │
└───────────┘   └───────────┘
```

Skill は **What to do / How to do** を与える。

Experience は **what actually happened** を保持する。

Meta-Judgment は、

> **いま自分が「やるべきだ」と思っていることを、どこまで信頼してよいのか**

を判断する。

この３つは、別々の知識形式のように思われます。

現在の Agent Skills は、１つ目の Skill Layer を急速に発展させています。

Agent Memory の研究は、２つ目の Experience Layer へ取り組み始めています。

そして、**まだ十分に整理されていないのが、３つ目の Meta-Judgment Layer なのではないか** と思います。

# In-context experience は「直感」として機能しうるのか？

ここで LLM には、従来のソフトウェアにはなかった面白い性質について言及してみましょう。

それは、**In-context learning** ができることです。

これは、追加学習でモデルのパラメーターを更新しなくても、追加のルールを Context として与えることで、その場で学習し、その後の判断自体を変えることができるという LLM の特徴のことです。

すでに LLM Agent 研究では、過去の Trial、Reflection、Trajectory、成功・失敗事例などを Context として与えることで、次の実行へ利用し、性能を改善する研究が多数行われています。

しかし、この能力を「正解率を上げるため」だけではなく、

> **Agent の判断姿勢そのものを変えるため**

に使うことはできないでしょうか？

たとえば同じ Skill と同じ未知タスクを与えます。

Experience を与えていない Agent は、

> 「条件を満たしているので、この Skill を実行します」

と判断する。

一方、過去の多様な episode を読んだ Agent は、

> 「形式上はこの Skill を適用できます。しかし、過去のいくつかのケースでは、同様に前提が綺麗に揃って見えたときほど、後から未確認の制約が発見されています。実行前に X を確認します」

と判断する。

もしこのような変化が起きるなら、非常に興味深いことです。  
これは単に、

**正答率が上がった**

のではありません。  
Agent の推論姿勢が、

**Execution-Oriented**

から、

**Risk-Sensitive**

へ変化したことになります。

言い換えれば、

> **In-context experience が、熟練者の Intuition（直感）の初歩的な代替になった**

と考えられる可能性があります。

もちろん、本当にそうなるかどうかは、実際に実験してみなければ分かりません。

# 何を評価すべきなのか

この仮説を検証する場合、従来的な判断基準だけでは足りません。  
「タスクを成功させたか」だけを測ると、重要な変化を見落とします。

むしろ、

- 疑うべきところで疑ったか
- 不足情報に気づいたか
- Skillが想定していない兆候を拾ったか
- 追加観測を選んだか
- より可逆的な行動を選んだか
- Skillの適用そのものを中止できたか

といったものを測る必要があります。

つまり、

> **Can the agent execute the skill?**

だけではなく、

> **Does the agent know when not to trust the skill?**

を測る。

これは Skill の評価そのものを変える可能性があります。

# Skill は「知性」ではなく、知性を構成する一部なのかもしれない

Agent Skills は、とても魅力的な枠組みです。

人間が長年かけて身につけてきた業務手順や判断基準を自然言語で記述し、AI エージェントにそのまま実行させられる。

これは人類の実務知を、実行可能な形へ外部化する大きな一歩になるかもしれません。

しかし、その可能性が大きいからこそ、

> **Skill に熟練そのものを期待しすぎない**

ことに留意が必要だと思います。

Skill は Procedural knowledge を外部化できます。

しかし熟練者は Procedural Knowledge だけで動いているわけではありません。

世界についての一般知識がある。

大量の Episode（体験談）がある。

失敗だけでなく、near miss や surprise がある。

そして、それらを背景に、

> 「今回は少し違うかもしれない」

と自分自身の判断を疑います。

もしそうなら、

```text
良い Skill
    ↓
良い Agent
```

という単純な構図ではなく、

```text
Semantic Knowledge
        +
Procedural Knowledge
        +
Episodic Experience
        ↓
    Meta-Judgment
        ↓
   Situated Action
```

という多層的なモデルで Agent を考えた方がよいのかもしれません。

# 人類は「手順」を AI に伝える手段を手に入れた。では「経験」はどうか？

考えてみると、人類は知識を共有するとき、長いあいだ経験を圧縮してきました。

- 経験から言葉を作る
- 言葉から概念を作る
- 概念から原則を作る
- 原則からルールを作る
- ルールからマニュアルを作る

Skill は、その延長線上にあります。

そして今までのマニュアルと大きく違うのは、Skill として記述されたルールを、AI エージェントが直接遂行できることです。

これは大きな変化です。

しかし、もし経験をルールへ変換すると、その圧縮過程で、私たちは何かを捨てています。

- 曖昧さ
- 例外
- 迷い
- 偶然
- 時間的な文脈
- まだ説明できない違和感
- 「なぜか分からないけれど、これはちょっと怖い」という感覚

これまで、そうしたものの多くは、人間の身体や記憶、職場の文化、師弟関係、レビュー、雑談、失敗談の中に残されてきました。

AIエージェントへ Procedural Knowledge を渡す技術は、急速に整いつつあります。

では、

> **Experience をどう渡すのでしょうか。**

そしてさらに、

> **Experience を使って、「いま自分が信じている Skill や Frame を疑う能力」をどう作るのでしょうか。**

これは、Agent Skills が成熟していく過程で、かなり重要な問いになるように思います。

Skill を書くことだけが、Agent に知識を与える方法ではないのかもしれません。

もしかするとこれから必要になるのは、

**Skill を教えること**

と同じくらい、

**経験させること**

なのではないでしょうか。

そして熟練した Agent とは、

たくさんの Skill を持つ Agent ではなく、

> **Skill を知り、Experience を持ち、それでもなお「今回は違うかもしれない」と疑える Agent**

なのかもしれません。

まだこれは仮説です。
しかし、十分に実験する価値のある仮説ではないかと思います。
